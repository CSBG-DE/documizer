01Overview

The Documizer reads what a system actually contains and turns it into a chaptered document. Every report writes the same XML format, which can be read back, and a self-contained HTML file for people.

ZDOCUMIZER_IMG

Customizing documentation

Reads a structure of the implementation guide, maps nodes to IMG activities, takes over SAP's standard documentation and reads the customizing behind each activity down to table contents. Can turn a document into a BC set.

ZDOCUMIZER_DEV

Developer documentation

Starts at a package or a single object — report, class, function module, table, view, CDS view, RAP objects, IDoc types, UI5 apps. Adds fields, components, text elements, source code, where-used lists and the objects used. Can import.

ZDOCUMIZER_ATC

Check configuration

Documents ABAP Test Cockpit and Code Inspector check variants: which checks run, with which message priorities, customer priorities, pseudo comments, pragmas and exemptions.

What people use it for

  • Documenting developmentsA package or an application with everything it uses, readable without system access.
  • Documenting IMG settingsThe customizing of a project or area, with SAP's explanation next to the actual table entries.
  • Transferring developmentsTables, structures, reports, classes, CDS and RAP objects, IDoc types and UI5 apps — into a system without abapGit or transports.
  • Transferring customizingAs a BC set that someone reviews and activates in SCPR20, never by writing to customizing tables directly.
  • Input for AI assistantsThe XML is complete and structured: a good basis for research, troubleshooting and extensive documentation with a model such as Claude.
  • Reviewing code standardsThe check configuration a system enforces, in one document you can compare between systems.

One source per report

Every report must run after being pasted into SE38 in any system — a customer system where nothing may be installed, no transport can be imported and abapGit is not an option. Everything else in the design follows from that:

  • No global classes. Chapter model, renderers and parser are local classes in each report, deliberately duplicated.
  • No text elements. All screen labels live in the source and are filled into SELECTION-SCREEN COMMENT fields at INITIALIZATION. Text elements are a separate program part and would not survive copy and paste.
  • No own repository objects. No Z tables, no Simple Transformation, no message class. XML is written and read with the kernel classes cl_sxml_string_writer and cl_sxml_string_reader.

Principles

  1. Standard APIs first. STREE_*, DOCU_GET, CL_PAK_PACKAGE_QUERIES, the DDIF_* modules. Direct table access only where no API exists or the API is too expensive.
  2. No system-specific data in chapters. Creator, timestamps and client appear only in <meta>. Otherwise comparing DEV, QAS and PRD is worthless.
  3. Two languages, two audiences. The document follows the output language; the run log follows the logon language of whoever started the run.
  4. Never silently incomplete. When a limit cuts something off, the document says so.

02Installation

A report is installed in seconds. There is nothing to transport and nothing to configure.

  1. In SE38, enter a program name, choose Create, type Executable program, and give it a title.
  2. Paste the complete source, save, activate.
  3. Run it. All field labels come with the source — English by default, German when you log on in German.

The program title is the only thing to set by hand. It lives in the text pool and cannot be filled from the source: SE38 → Goto → Attributes.

In-system report documentation

Documentation objects are separate repository objects, so they do not travel with the source either. The helper report ZDOCUMIZER_DOCU writes the SAP report documentation for ZDOCUMIZER_IMG, ZDOCUMIZER_DEV and ZDOCUMIZER_ATC in the target system. Run it once after installing or updating; the text then appears in SE38 under Documentation and behind the information button of each selection screen.

HTML

One self-contained file: embedded CSS, no JavaScript, no external dependencies — it should still open in years without rework. It has a table of contents over the top two levels, numbered chapters, data tables and source code blocks. The HTML is rendered from the chapter model, not from the XML, so there is no second parser path that could drift.

SAP documentation arrives as ITF. Section markers such as &USE&, &DEFINITION& or &EXAMPLE& become subheadings, highlighting and links become bold text. Markup is balanced per line — in ITF a tag may run across lines, and an unclosed one would colour the rest of the page. The XML keeps the ITF unchanged; lossless storage matters there, formatting belongs to the display.

Large blocks are collapsed. A 2,000-line source or an 800-row table would push everything else out of view. Anything longer than Collapse HTML from lines appears as a summary line with label and size, for example Where-used list (312 entries), and opens on click. It is a plain <details> element; a viewer that does not know it simply shows the content expanded.

Definition data never reaches the HTML. The HTML renderer does not touch the <definition> block at all, so base64 file contents, name/value attributes and technical settings stay in the XML. The readable document stays readable.

Storage

Download to PCdialog onlyFront-end services do not exist in background jobs

Both paths write binary after converting to UTF-8. A text download would convert into the front-end code page, which is exactly where umlauts and other characters get lost.

File name

File name holds the name without extension: XML and HTML come from the same run and differ only there. The proposal is built from report, system ID, start object, date and time — for example documizer_dev_DV1_z_report_20260901_083000.

  • The proposal is rebuilt on every screen round trip, so it follows the start object. The field is only overwritten while it still holds the previous proposal; a name you typed yourself stays.
  • Namespaces such as /BOBF/OBJ contain slashes, which separate directories. They become underscores.
  • In background jobs and with SUBMIT no PBO fills the proposal. If the field is empty, the report builds the name itself when writing.
  • For a request list (type AL) the object part is left out. The IMG report uses the structure ID or the project instead; the search term is prose and stays out.

What happens in a run

  1. Read the structure with STREE_HIERARCHY_READ_ALL_SUBS — not STREE_HIERARCHY_READ, which stops at the references to substructures.
  2. Classify nodes. A node with reference type COBJ in TNODEIMGR is an activity chapter; all others are outline chapters.
  3. Enrich each activity: header data from CUS_IMGACH (documentation ID, transaction), title from TNODEIMGT or CUS_IMGACT, documentation via DOCU_GET with class HY, object assignment from CUS_ACTOBJ.
  4. Read customizing according to the volume controls below.
  5. Overlay project data if a project is given.
TNODEIMG      node, hierarchy via PARENT_ID / BROTHER_ID
└─ TNODEIMGR  REF_TYPE = COBJ, REF_OBJECT = IMG activity
   └─ CUS_IMGACH  ACTIVITY, DOCU_ID, TCODE
      ├─ DOKHL        documentation class HY  → DOCU_GET
      ├─ CUS_ACTOBJ   object type and name    → base table
      └─ CUS_IMGACT   language-dependent title

The documentation class is HY, not SIMG. DOKHL-ID is two characters long; SIMG is the prefix of the documentation object name ('SIMG' + ACTIVITY). With the wrong class DOCU_GET returns empty texts without an error.

Customizing contents

The object type in CUS_ACTOBJ decides how an object is read:

TypeMeaningHandling
VViewresolved to base tables (DD25L, DD26S)
CView clustersplit into views via VCLSTRUC, then like V
TTableread directly
SMaintenance dialoglike V
DDummyno data, only the transaction

Views and view clusters are always resolved to their transparent base tables. A maintenance view cannot be read with SELECT, a base table always can — the distinction between database and maintenance view disappears.

Customer entries and volume

Customizing tables range from three rows to millions. Volume is controlled in three steps:

  1. Read customizing data off → structure only, no data.
  2. Customer entries only → two methods at once, combined with OR: the namespace of the first business key field (Y, Z, /) and the occurrence in transport requests (E071K) for this table. The namespace also finds customizing that was never transported; the transport check also finds keys outside the customer namespace.
  3. Max. rows → hard limit per table. When it is reached, the total row count appears in the document.

Which method applied is recorded on the object, not only in the log — otherwise nobody can later tell why a table shows three rows:

filterMeaning
NAMENSRAUM+TRANSPORTboth methods active
NAMENSRAUMnamespace only, no transport entries found
ALLEflag off, or filter not applicable
GESPERRTno read authorization (S_TABU_NAM) — the object appears with a note, it is not silently dropped

Project mode

TNODEIMG node ──▶ CUSSTAT  project + node + status GUID ──▶ TSTAHTPR  memo in COMM1…COMM5

An IMG project carries status, progress and a memo per activity. Access runs through the node GUID, independent of the structure the tree came from; the five 50-character comment fields are joined back into one text.

With Project nodes only, outline chapters stay as long as a project node hangs below them — otherwise the hierarchy would fall apart. Chapter numbers keep their position in the uncut tree, so gaps show that something was left out.

The entry point is derived. In this mode the report ignores the structure ID and reads only the structures that contain project nodes. Substructures are not resolved: the project root is one of the project nodes, and its structure is the complete guide. The chapter limit is suspended while traversing, because project nodes are often deep in the tree. In practice: half a second instead of an abort.

Outgoing references

Behind an activity there is a transaction and behind that a program. With Outgoing references its source is scanned for function modules, table access and classes. Only the transactions of the assigned objects are used, never the one on the activity header — that is almost always a parameter transaction into the IMG framework and would pull SAPLS_CUS_IMG_ACTIVITY with all its BM_*, CTO_* and DDIF_* calls into every chapter. Parameter transactions of the objects are followed one step via TSTCP.

Chapter structure

1  <root node>                          outline chapter
   1.1 <subnode>                       outline chapter
       1.1.1 <IMG activity>            activity chapter
             ├─ description            DOCU_GET (class HY), ITF resolved

Why a BC set and not direct access

The report creates a Business Configuration Set and with that writes nothing yet. Customizing only arises when someone activates the set in SCPR20. Activation comes with a log, with a transport request, with the chance to look inside first and with a way back. A report issuing MODIFY on a customizing table has none of that.

The set is written with SCPR_PRSET_DB_SAVE_ORIG_TABLES, which runs without a dialog — unlike almost everything else around BC sets. Two properties are easy to miss: the module checks nothing, and all seven tables must be passed (SCPRVALS, SCPRVALL, SCPRRECA, SCPRSKEYS, SCPRFLDV, SCPRTEXT, SCPRPPRL). One left out is not left alone — it is deleted. Field values carry KEY or USE; MANDT travels as a key field with an empty value, because the client is fixed at activation, not at creation.

What goes in

Blocked whenReason
Table unknown hereA set on a table that does not exist cannot be activated.
Delivery class not C, G or EAnything else is not a customizing table.
Contents truncated at exportThe most important one. Contents cut at Max. rows look complete in the set — and on activation, whatever did not come along disappears.

For a complete transfer, export with Max. rows = 0. Every skipped table is logged with its reason. Duplicates are removed by table name, and after the checks — a table skipped for truncation must not block the same table coming from another activity. On a real customer export that meant about 300 duplicate records out of 1,472.

The request list

A BC set can only carry tables that exist in the target system. Customer-defined customizing tables are exactly the ones that do not — they are development and have to arrive first. So on request the IMG report writes a request list of the objects it had to skip: 

<documizer version="1.0" type="REQUEST">
 <meta><system>QS1</system><source>DV1/100</source></meta>
 <objects>
  <object type="TABL" name="Z_SKIP_IND"  activity="ZV_SKIP_IND"/>
  <object type="VIEW" name="ZV_SKIP_IND" activity="ZV_SKIP_IND"/>
 </objects>
</documizer>

The development report in the source system reads this file as start type AL and exports exactly these objects. Once they are imported, BC set creation succeeds for them as well. The circle closes: customizing needs the tables, the tables arrive through the development report, and the target system itself says what is missing.

Per maintenance object the list requests the table, for maintenance type V/S also the view, for C the view cluster, plus the maintenance transaction. Since format 1.1 the maintenance object is stated on the <object> tag (objtype, objname); older documents are still read and yield only the table entries.

Only what is really missing is requested. The first run asked for SM30 — a standard transaction present in every system. A request list that asks for existing objects costs the developer in the source system time and trust. Each type is checked against DD02L, DD25L, VCLDIR or TSTC.

Documenting a transport request

With TR the name field takes a request or task number; the value help shows your own requests, the most recent first. What comes out is a document about exactly what this transport contains — with details, source code and where-used lists, like any other start point. The header names the kind and status of the request, its short text, owner, date, target system and the tasks below it.

The objects hang off the tasks, not the request. A request's own object list is regularly empty — what travels sits in the tasks below it, so both levels are read. Give a task instead and you get that task alone, with the request named in the header.

Parts are rolled up to their object. Besides whole objects a request also lists single methods, includes and table definitions. What gets documented is the object the part belongs to, and each one only once — the translation comes from the same function module the correction system uses for it.

Whatever is not a documentable object is named up front rather than silently dropped: customizing entries with their table and number of keys and a pointer to the IMG report, deletions, entries without a catalog object, and objects that no longer exist in the system.

Released or modifiable. A released request documents what was in it; a modifiable one, what is in it right now. The second case says so in the header — otherwise the two read the same.

Package mode

Packages come from CL_PAK_PACKAGE_QUERIES=>GET_ALL_SUBPACKAGES, objects per package from GET_DEV_OBJECT_TADIR_KEYS, grouped by object type. Both methods raise classic exceptions: without an EXCEPTIONS clause each one ends in a short dump, and TRY…CATCH does not help. Packages without a TDEVC or TADIR record exist in real systems; they appear with a note instead of aborting the run.

Deleted objects stay out. When an object is deleted, its catalog entry remains in TADIR with DELFLAG = 'X' until the request containing the deletion is released — and the package API returns it. The document then listed a class that no longer existed, with an empty short text. The package loop reads the deleted entries once and skips them; name resolution against TADIR checks the flag everywhere.

The package boundary holds. In package mode the package is the subject. What its objects use outside the package appears in the reference list, but is not documented as a chapter. To document an application together with its neighbourhood, start from the object that carries it — for a RAP application the root CDS view (type W) — with reference depth 2.

IDoc segments and CDS views

Both keep their field list somewhere else than expected. An IDoc segment is a flat character structure in DD03L — every field is CHAR without a data element. The data element WE31 shows is stored only in EDSAPPL under the segment type. A CDS view has at most its SQL view in DD03L, and a view entity or custom entity has none; the elements are in DD03ND under the entity name that DDLDEPENDENCY lists as STOB. A field without a data element shows data type and length.

So the source is scanned as well. Comments are cut off first, and every hit is checked against the catalog before it enters the document — function modules against TFDIR, tables and classes against TADIR, with one query rather than one per hit. Local classes, work areas and runtime-built names drop out; dynamic access such as FROM (lv_tab) does not match the pattern.

The list is sorted by kind — function modules and reports, table access, method calls, types, data objects — so that when the limit applies, what readers look for first stays on top. References are stored under the include, not the object name; for a function module (L<group>U<nn>) and its group (L<group>) that is not the same. The reference list is drawn only for objects whose references were actually followed; for the leaves of the tree it would be dead weight.

Names in character literals

MOVE 'Z_ALV_STRUCT' TO lv_structure_name.   " ALV field catalog

The structure is needed at runtime but named nowhere statically. No index knows it, and the workbench where-used list does not show this program as a user. The literal is the only trace. The scan collects every literal that could be an object name and checks it against TADIR; a literal with spaces does not match, so ordinary text drops out by itself. Objects found carry the note used dynamically.

That is an assumption, not a finding. A literal that happens to look like an object name ends up in the document. The price is small — and the gain is the difference between a document that imports and one that misses an object at activation.

Includes

INCLUDE Z_REPORT_TOP. is a static reference, yet it is in no cross-reference index and matches no call pattern — and without it the program does not compile. It is taken from the source, not from RS_GET_ALL_INCLUDES: that module answers from D010INC, which is filled at generation, so a transported but never executed program reports no includes. D010INC also lists the generated sections of every class used (CL_…====CU). INCLUDE TYPE and INCLUDE STRUCTURE are something else and are excluded.

Composition is not limited, usage is

Max. entries per object limits how many usages are collected — that number is open-ended and the scan is expensive. What an object consists of is always collected completely: the data elements of a table, the domain of a data element, the base objects of a CDS source. That number is bounded by the object itself.

It was different at first and produced a bug that is hard to see: a structure with 53 distinct data elements against a limit of 50. Three were dropped, and since a SELECT without ORDER BY has no reliable order, the database decided which. The document showed the structure complete, one data element was missing, and on import the structure did not activate.

For an IDoc segment the data elements come from EDSAPPL, not DD03L. Measured on a custom basic type with definition data:

Where-used list

By default only for the start object. The question "who uses this" is about the entry point, not its neighbourhood — a data element such as CHAR255 is used by thousands of SAP programs and would bury the document under its own list. In package mode every object is the subject and gets its own list.

Per hit the document shows:

  • the program kind from TRDIR-SUBC — report, function group, class pool, module pool, subroutine pool, type group; a function group with its name rather than the main program SAPL<group>.
  • for a table the access type: read, write or both. The index only knows that the table occurs; the include it points to is scanned, not the main program — in a function group the SELECT sits in LZ…F00.
  • the occurrences with line number and statement, like SE11 shows next to its hit list. With Occurrences in full source, the complete source with hit lines in bold.
  • for a table or structure the fields touched. WBCROSSGT stores a field usage as <structure>\TY:<field>; searching the bare structure name finds none of them. The search uses LIKE … ESCAPE, because the underscore in a name is otherwise a wildcard. Hits are merged into the list — one line per location, the fields behind it, for example fields MAKTX, SPRAS at E1MAKTM. This is the list SE11 shows as where-used list for structure field.

An include can belong to several main programs. Only a unique main program is named; otherwise the include stands alone. Presenting a guess as a fact would be worse than no statement. For a table the list also names the views and CDS views built on it: DD26S knows the base tables of a view, DDLDEPENDENCY the objects behind a CDS view.

also for used objects. For an IDoc basic type the trade-off turns around: nobody types the basic type, but its segments are read all the time — the question is about the neighbourhood. With this flag the where-used list is drawn for every object in the document. It is off by default so that existing variants behave as before; Max. entries per object still applies per object.

Exclude SAP standard

The measure is the delivery unit of the package (TDEVC-DLVUNIT): HOME and LOCAL are own development, everything else was delivered. That is the line SAP itself draws, and unlike a name check for Z and Y it also catches customer objects in reserved namespaces and SAP objects that start with Z. For a function module its function group decides.

Anything without a catalog entry counts as not own — constants of a type group such as ABAP_TRUE, kernel types — with one exception: an include found in the source of an object already in the document often has no catalog entry. What nobody catalogued is not SAP standard, so it stays. The filter applies to reference lists, never to the subject of the document.

09XML format

The XML is the leading format: complete, versioned and readable back into the same model that produced it. 

<documizer version="1.1" type="IMG">
  <meta>
    <system>DV1</system>
    <client>100</client>
    <created_by>…</created_by>
    <created_at>2026-09-01 10:00:00</created_at>
    <language>E</language>
    <truncated>false</truncated>

      <reference activity="…" docu_id="SIMG…" tcode="…"/>
      <documentation format="ITF" lang="E">&USE& …</documentation>
      <object type="T" name="T001" rows="42" truncated="false">

For type="DEV" and type="ATC", meta and chapters are identical; the object kinds differ (CALLS, USAGE, SOURCE, FUNC, …), and development chapters add a <definition> element. The HTML heading comes from the document type, so each report's document is titled correctly.

Rules

  • version from the start. Without it, a later format change cannot be handled cleanly.
  • truncated and rows on every data block, plus node_total against node_limit for the tree. A document must never be incomplete unnoticed.
  • Documentation as raw ITF, converted only when rendering HTML — lossless for reimport.
  • No timestamps or users in chapter data — only in <meta>.
  • Extend, don't change. A new attribute on an existing element breaks every document written before. Where an extension was unavoidable — the definition data — it lives in new elements an older parser skips, and the version went to 1.1.
  • Source code belongs in elements, never attributes. XML normalizes line breaks inside attribute values to spaces, silently. Hence <source>, <defsource> and <src>.

Roundtrip self-test

Check roundtrip renders the model to XML, parses it, renders again and compares character by character. The log shows identical — passed or a deviation. It protects the import: whatever is lost on the way there and back shows up here, not in the target system. Every format extension was built on only after a passed roundtrip. The XML is produced for this test even when Create/show XML is off.

Definition data

Up to format 1.0 the XML carried the description of an object, not its definition. A field list reads well but is not enough to create a table: delivery class, table category, technical settings and foreign keys are missing. Since 1.1 there is a separate element: 

<definition kind="TABL">
  <attr name="TABNAME"  value="Z_TABLE"/>
  <attr name="TABCLASS" value="TRANSP"/>
  <attr name="CONTFLAG" value="A"/>
  <row tag="DD09V"/>
  <row tag="DD03P">
    <attr name="FIELDNAME" value="MANDT"/>
    <attr name="POSITION"  value="0001"/>
    <attr name="KEYFLAG"   value="X"/>
    <attr name="ROLLNAME"  value="MANDT"/>
  </row>
  <defsource>…</defsource>
</definition>
  • The same structures in both directions. Export reads what DDIF_TABL_GET returns; import hands it back to DDIF_TABL_PUT — DD02V, DD09V, DD03P, DD05M, DD08V, DD35V, DD36M; DD01V/DD07V for domains, DD04V for data elements.
  • Name/value pairs instead of a structure per type. Structures are walked with RTTI, so renderer and parser need no type knowledge. A field the target release does not know is skipped instead of aborting. Initial fields are left out.
  • Its own source. <defsource> is complete, while the source shown to readers may be cut by Max. lines per object. Half a report reads fine; it does not import.
  • .INCLUDE is resolved. The RTTI walk uses get_included_view( ). get_components( ) returns an include as one nested component that the "elementary fields only" filter would drop — DD09V has 1 component against 21 in the resolved view.
  • Field names that are not valid XML names (*_ENTRY, 2_DIMENS in RPY_DYFATC) are written through a fixed, reversible substitution: * → _xas_, / → _xsl_, - → _xmi_, . → _xdt_, leading digit → prefix _n. A character without a mapping drops the field rather than making the document unreadable.

Text elements and documentation in all languages

Like messages, these are definition data, not description. The text pool of a program was first read only in the output language and imported into the logon language of the person importing: an English-maintained report imported by someone logged on in German had German selection texts with English content and no English ones at all. Now the text elements of every language (REPOTEXT) are exported, each TPOOL row with its language in _SPRSL.

Object documentation of programs (RE) and data elements (DE) travels as a DOCU row per language from DOKHL, with attribute LANGU — independent of Object documentation. The chapter shows documentation to readers only with that flag and in one language; the definition data always carries all of it, as ITF with format and text separated by a tab.

Two safety rules

  • Test run is on by default. Every step reports what it would have done. Writing requires deliberately removing the tick.
  • Existing objects stay untouched unless Overwrite existing objects is set. A documentation tool must not replace a table silently.

Picking and renaming

Rename or skip objects puts a list in front of the import: one row per object in the document, prefilled from exactly the worklist the import will work through. Two columns can be changed — target name and target package — plus a tick column Skip.

Renaming applies to the whole document, not just to the object name: the new name replaces the old one in the source code as well, word for word and regardless of case, in SELECT FROM old as much as in TYPE REF TO old. The word boundary prevents partial hits — ZKUNDE leaves ZKUNDE2 alone. The target name has to be in the customer namespace and unique per object type; that way even an SAP object can be brought in under a Z name without overwriting the original.

Skip takes the row out of the run entirely. The object is neither created nor changed, and it is not verified afterwards — the filter sits before the first write. A skipped row needs no target name and is not renamed; otherwise the replacement would run over an object that never arrives. Every skipped row is named up front in the header of the list and gets a log line, so that leaving it out is documented rather than looking like a failure.

Dependencies are not enforced. Skip a domain whose data element is imported and you get the familiar activation error — the log names the missing object. The report warns about it but does not forbid it: often the skipped object exists in the target system already and is precisely what should not be touched. The list is available in dialog only; in the background the run says so and imports without it.

What would change

A test run that only says would be changed withholds the essential part. For every object that already exists in the target system, the test run therefore compares the source: 

CLAS  ZCL_MAILER   source differs   +12 / -3 lines
        12   DATA lv_a TYPE i.
        13 - lv_a = 1.
        13 + DATA lv_b TYPE i.
        14 + lv_a = 2.
        15   WRITE lv_a.
       ... 240 lines unchanged

New lines in green, dropped ones in red, two lines of context, unchanged stretches summarised. The number on the left is the line number of the side the line belongs to. If nothing differs, the log says source identical with the line count — that is an answer too.

The old state is read from the target system in the same composition the export produces: programs through READ REPORT, function groups with the frame program and the includes in export order, classes and interfaces as the source-based form, CDS sources from the DDL table, behavior and service definitions through the workbench operator. Any other composition would produce differences that are none.

The comparison is a windowed match: identical lines run in parallel, and at a difference it looks ahead up to sixty lines for the sides to meet again. The grouping is therefore not always the tightest — the content always is: every line appears exactly once, and the result can be replayed in both directions.

Two cases stay without a comparison, each with its reason: an object that does not exist in the target system yet — there will be created says everything — and a source that was cut at the line limit during export, which would otherwise report the missing remainder as deleted. Objects without one continuous source — DDIC objects, IDoc, UI5 — stay with would be changed for now.

Order

The report sets the order itself: domains, data elements, tables and structures, views, CDS sources, programs, interfaces, classes, function groups, then view clusters and transactions. A table whose data elements do not exist yet cannot be activated, and a cluster without its views cannot be opened; sorting the work first is cheaper than repeating it. Secondary indexes are created per table once the table is active.

Which package

Without further input everything lands in the target package. To keep or redirect the source system's package structure, use the four rules old → new: left the package the object was in over there, right the package it should land in here — for example $TMP → Z_PACKAGE1. The source package has always been in the document; the export writes it into the object reference.

PriorityTarget package per object

3otherwise the target package from the screen
  • A package that does not exist here is not created. That decision belongs to a developer. The object goes to the target package, and the log says why — one line per rule, not per object.
  • The request follows the package of each object, not the screen input. A local package needs no request, a transportable one does. Redirecting $TMP to Z_PACKAGE1 attaches the request even if the target package on the screen was local.
  • No request for a transportable package does not stop the catalog entry: TR_TADIR_INTERFACE creates it without a dialog and without a request. The log warns once per package.
  • Documents from an older version carry no source package; the target package applies.

Request and task

An object is not recorded in the request itself but in a task under it — and a released task accepts nothing. When you have no open task, the transport organizer would normally ask in a dialog. An import has no dialog, so it refuses — for classes with NO_ACCESS, which looks like missing authorization. The real message reads No matching task exists under request … for user ….

Create task if needed therefore checks before the run whether the request from the screen has a modifiable task (status D or L) for the logon user, and creates one via TR40_TASK_ADD otherwise — without a dialog, only under that request, never in a test run. Without the flag you get a warning up front instead of an abort halfway. If you enter a task instead of a request, it is recognized and left alone.

No COMMIT WORK, no request entry. The transport organizer writes through the update task; request entries and new tasks exist only after the commit. Without it a run reported a new task that the transport organizer never showed. The importer commits at the end of the run, before the post-run check, and not in test runs.

Text elements and documentation

Text elements are written with one INSERT TEXTPOOL … LANGUAGE per language, documentation with one DOCU_UPDATE per DOCU row. The log names languages and counts: 

PROG Z_REPORT_COPY  created                560 lines

A document from an older version carries neither _SPRSL nor DOCU rows; then the previous behaviour applies — text pool into the logon language, the chapter's documentation text in its language.

The log

Per object the log gives type, name, what happened — created, changed, skipped, error, not possible — and why. An error line carries the real return code and the message of the SAP module:

  • ABAP evaluates the actual parameters of a method call in the order of the interface, not of the source text. In the log call the action text is translated first, which resets sy-subrc before the string template reads it — every error line used to say subrc 0. The code is now stored in a variable right after the call; swapping the parameters in the call would not help.
  • The called modules issue a message before their RAISE (MESSAGE … RAISING). It is read from SY-MSGID, SY-MSGNO and SY-MSGV1..4 immediately and appended. A 5 does not say whether authorization, a lock or the transport organizer refused; the message does.

Activation. The DDIF_*_ACTIVATE modules return 0 for clean, 4 for "activated with warnings" and 8 or more for failed; only from 8 does the object stay inactive. Treating 4 as an error would abort at a perfectly usable table and skip the follow-up steps. From 8 the log names the likely cause: the object the failed one depends on that does not exist in active form — the domain under a data element, the data elements under a table or view, at most three. 

DTEL Z_ACTION  DDIF_DTEL_ACTIVATE rc 8  missing or inactive: domain Z_ACTION_D

Targeted activation. Classes and function groups are created inactive and activated with RS_WORKING_OBJECTS_ACTIVATE — using a list the importer builds itself. Of the user's inactive objects it takes only those belonging to the object just written. The inactive list usually holds the importing user's own unfinished work; activating it wholesale would switch someone's half-done changes live.

Tables, indexes and CDS sources

DDIF_TABL_GET returns secondary indexes as DD12V/DD17V, but DDIF_TABL_PUT does not accept them. They travel as rows of the table definition and are created with DDIF_INDX_PUT once the table is active. The field DBINDEX is cleared — it holds the database name built from the table name and would otherwise still name the source table.

CDS sources have no DDIF_* module. CL_DD_DDL_HANDLER_FACTORY=>CREATE( ) is the only way: save, attach to the catalog, activate. Saving needs PUT_STATE = 'N', the new inactive version; 'M' is a read state the handler rejects there. It is the one place the importer uses an SAP-internal class instead of a function module.

Reports and the GUI status

INSERT REPORT carries the source and nothing else. Menus, function keys, toolbar and titles are a separate program part; a report that sets its own status would end in CX_SALV_OBJECT_NOT_FOUND or shortly after. RS_CUA_INTERNAL_FETCH and _WRITE are a symmetric pair over eleven tables (STA, FUN, MEN, MTX, ACT, BUT, PFK, SET, DOC, TIT, BIV) plus the header RSMPE_ADM. The directory entry is cleaned of author, dates and versions from the source system.

Classes and function groups

Classes and interfaces travel in their source-based form — the single text SE24 and ADT show, definition and implementation together — read and written through CL_OO_FACTORY and IF_OO_CLIF_SOURCE. The generated includes of the class pool cannot rebuild a class. The header (VSEOCLASS / VSEOINTERF) travels separately; author, change date and UUID stay in the source system — the UUID identifies exactly that class, and a copy must not carry it.

A function group consists of several sources, so each row carries its own <src>: the TOP include, all hand-written includes and each module body. The includes generated when modules are created (L…U01, L…UXX) are skipped, otherwise they would be created twice. RPY_FUNCTIONMODULE_READ returns the whole include with FUNCTION, interface comment and ENDFUNCTION, while _INSERT generates those itself — the importer strips them, or the module ends with ENDFUNCTION twice.

Nothing is published. Whether a binding was published in the source system is recorded, but the import always creates it unpublished. Creating a binding is a development task; exposing an OData service is a different decision nobody should make in passing. The binding's own label does not travel — no API used returns it; the object name takes its place.

UI5 applications

The frame is a BSP application, the files are its pages — Component.js, manifest.json, i18n/i18n.properties and the rest, with directory path and case. Files are read and written through the UI5 repository API (/UI5/CL_UI5_REP_DT), the same path ADT takes: the export walks the tree (GET_FOLDER_CHILDREN, CHECK_IS_FOLDER) and fetches each file with GET_FILE; the import creates folders, then files with PUT_FILE, framed by LOCK and UNLOCK. CREATE_REPOSITORY creates BSP application, MIME folder, ICF node and catalog entry.

The bytes travel as base64 — one rule for text and binary, no guessing about encodings. That costs about a third: a measured app with 21 files and 100,905 bytes gave a document of 139,190 characters; a freestyle app with libraries lands in the tens of megabytes. The path mapping file itself does not travel; it is bookkeeping of the target system and is rebuilt there. A measured roundtrip returned the same directory tree, and manifest.json and i18n.properties came back character for character.

IDoc types

An IDoc segment type is catalogued as TABL, because SAP generates a DDIC structure of the same name. Imported as a structure, the target system would get something with the right fields that WE31 does not know as a segment. The worst kind of gap: one that looks right. So for every TABL the export checks EDISEGMENT and treats a hit as a segment. SEGMENT_CREATE creates segment type, segment definition and structure in one go; header is EDISEGMHD without timestamps, fields are EDISEGSTRU rows.

A basic type uses IDOCTYPE_READ/_CREATE/_UPDATE with header EDI_IAPI05 and the hierarchy as EDI_IAPI02 rows. It pulls its segment types along: the hierarchy is in the syntax table, not in any cross-reference index. Existence is checked through the API, not EDISYN — that table holds only the released syntax and stays empty for a newly created type.

To create a basic type in another system, export with definition data and reference depth 3: segments, their data elements and the domains behind them. With depth 2 the domains are missing — the custom data element does not activate, the segment fails on it and the basic type on the segment.

An existing segment is never touched, not even with Overwrite existing objects. Appending a segment definition creates a new version, which is a developer's decision.

SEGMENT_CREATE takes DEVCLASS and ORDER as CHANGING parameters, not EXPORTING. Passed in the wrong block, the call ends in CALL_FUNCTION_PARM_UNKNOWN — at runtime only, because CALL FUNCTION with a literal is resolved at runtime. After that finding all 13 writing function modules of the importer were compared against FUPARAREF: 48 parameters, no further deviation.

Message classes

A report whose message class is missing shows the bare key instead of the text: S:Z_MSG_01:006. That is not a language problem — when the class exists but is not maintained in the logon language, the runtime falls back to English. The key form always means class or number do not exist.

  • Message classes are found in the source: the MESSAGE-ID addition of the program header and the bracket form after a number (MESSAGE s006(z_msg_01)) — neither is a quoted literal nor in an index.
  • RPY_MESSAGE_ID_INSERT opens a catalog dialog even for $TMP, so T100A and T100 are written directly and read from the same tables.
  • All languages, not the output language. A class maintained only in English, exported into a German document, would otherwise arrive without a single message — and that is the normal case.
  • Existing texts stay. Missing numbers and languages are added; texts already there may have been translated or corrected.

12Authorizations & runtime

Authorizations

The IMG report checks S_TABU_NAM before every table read. Without authorization the object appears with a note (GESPERRT) instead of silently staying empty; a documentation tool must not work around read authorizations.

The import is the only place the Documizer writes. The called SAP modules check S_DEVELOP against object and package, and that check stays switched on: AUTH_CHK / AUTHORITY_CHECK are set everywhere. Without the rights the module refuses and the log shows it. Switching the check off would be one line — and would turn the report into a tool that creates repository objects someone could not create by hand.
